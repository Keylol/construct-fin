# IJ9 — ОПиУ по реализации (accrual по closedAt)

Дизайн-документ по закрытию IJ9 (council-registry: маржа атрибутирует период по
`Order.closedAt`, ОПиУ — по датам платежей → одна продажа в разных месяцах двух
отчётов; внутри самого ОПиУ базисы уже смешаны — COGS услуг датируется выдачей).

## Решения владельца (блиц 2026-07-14)

1. **Базис ОПиУ для заказов — по реализации (`closedAt`).** Выручка и
   себестоимость заказа признаются в месяце выдачи. ОДДС остаётся строго
   по движению денег (cash) — не трогаем.
2. **Авансы** (деньги, полученные до выдачи) в ОПиУ не показываются —
   видны в ОДДС, на счетах и в дебиторке.
3. **Возвраты клиента (RMA)** — минус выручки и COGS в **месяц возврата**
   (закрытые месяцы не переписываются задним числом).
4. **Drill-down «Выручка»** из ОПиУ ведёт в **заказы, закрытые в периоде**
   (сумма сходится с цифрой отчёта), а не в операции-платежи.
5. **«Закупки»** — информационная строка вне итога (как «Капитал
   собственника»): склад = актив, расход признаётся как COGS при продаже
   и списаниях. Прибыль перестаёт проседать в месяцы больших закупок.
6. **Частичная отгрузка** — признание целиком при закрытии заказа
   (только DONE, как отчёт маржи). Открытые частично отгруженные заказы
   в прибыли не видны.

## Целевая семантика ОПиУ

Для периода P (границы в бизнес-таймзоне UTC+5, как сейчас):

- **REVENUE** =
  Σ по DONE-заказам с `closedAt ∈ P`: `qty × unitPrice` (gross, без вычета возвратов)
  − Σ по событиям возврата с `date ∈ P`: `qty × unitPrice-снимок`
  + ручные INCOME-операции с категорией бакета REVENUE по дате операции.
- **COGS** =
  Σ по DONE-заказам с `closedAt ∈ P`: `qty × (unitCostAtSale ?? unitCost ?? 0)` (BR1)
  − Σ по событиям возврата с `date ∈ P`: `qty × unitCost-снимок`
  + WRITE_OFF-проводки по дате (потери запасов, F4).
- **PURCHASES** — считается как сейчас (PURCHASE/SUPPLIER_REFUND по датам),
  но помечен `informational`: НЕ входит в grossProfit и net (аналог CAPITAL).
- **FIXED / VARIABLE / TAX / OTHER** — по дате операции, без изменений.
  Комиссия рассрочки (VARIABLE_COST при заказе) остаётся расходом по дате.
- **CAPITAL** — как сейчас (вне net).
- Проводки `ORDER_PAYMENT` / `ORDER_REFUND` в ОПиУ больше **не участвуют**
  (это движение денег → ОДДС). COGS-проводки заказов (услуги) в ОПиУ тоже
  не участвуют — себестоимость берётся из позиций (единый источник с маржой);
  сами проводки остаются для аудита и не двигают ОДДС (NON_CASH).
- `grossProfit = REVENUE − COGS`;
  `net = REVENUE − COGS − FIXED − VARIABLE − TAX + OTHER.income − OTHER.expense`.

## Модель данных: событие возврата

`OrderItem.returnedQty` — накопительный счётчик без даты; «месяц возврата»
требует событийной записи. Новая модель **`OrderReturn`**:

| поле | что |
|---|---|
| workspaceId, orderId, orderItemId | привязка |
| qty | возвращённое количество (событие, не накопительно) |
| unitPrice | снимок цены позиции на момент возврата |
| unitCost | снимок себестоимости (`unitCostAtSale ?? unitCost ?? 0`) |
| refundAmount | сколько денег вернули этим событием (инфо) |
| date | дата возврата (бизнес-семантика) |
| createdById, createdAt | аудит |

Пишется атомарно в `order.service.returnItem()` рядом с инкрементом
`returnedQty`. Возвраты возвратов/undo — вне скоупа (как и сейчас).

**Backfill истории** (миграция, best-effort, все строки помечаются в
`description`/`reason` как BACKFILL):
- склад: `StockMovement RETURN_CUSTOMER` (дата события известна; матчинг
  позиции по `refId=orderId` + `warehouseItemId`, при неоднозначности —
  первая подходящая позиция);
- остаточный `returnedQty`, не покрытый движениями (ручные позиции), —
  событие датой `Order.closedAt` (лучшее доступное приближение).

## Известное приближение: скидка при возвратах

Скидка заказа — order-level и вычитается из признания целиком в месяце
закрытия (`totalAmount`; в марже byClient — IJ1). Событие возврата минусует
`qty × unitPrice` — ПОЛНУЮ цену позиции, без пропорции скидки: позиционной
скидки в модели нет. При полном возврате заказа со скидкой сумма минусов
превысит признание на размер скидки (строка/период уйдут в минус на неё).
Осознанное приближение — скидки редки, пропорциональное размазывание
скидки по позициям добавило бы сложности без выигрыша в точности итогов года.

## Согласование отчёта маржи (И3)

Маржа сейчас неттит ретро (`netQty = qty − returnedQty` в месяце `closedAt`).
Для согласования с решением №3 маржа при периодном фильтре переходит на ту же
семантику: gross по `closedAt ∈ P` минус события возврата `date ∈ P`
(отрицательные вклады в строку товара/клиента). Без периода (вся история)
итоги совпадают с текущими (Σ событий == Σ returnedQty).

## Волны реализации

- **И1** — схема `OrderReturn` + запись события в `returnItem()` + backfill-миграция + тесты. (Грабли: partial-unique индексы → `migrate dev --create-only`, выпилить DROP INDEX.)
- **И2** — `pnl.service` на новую семантику (+ informational-флаг PURCHASES в ответе) + тесты, включая сверочный тест «ОПиУ.grossProfit == маржа.totals» на общем периоде без возвратов.
- **И3** — `margin.service` на события возврата (месяц возврата) + сверочный тест с возвратами.
- **И4** — фронт: подписи «по реализации», «Закупки (не входит в прибыль)», drill-down «Выручка»/«Себестоимость» → /orders c фильтром по периоду закрытия, дашборд-KPI на тот же базис.

Каждая волна — отдельный PR с Haiku-ревью; после мержа — проверка факта БД на проде (не только зелёного деплоя).

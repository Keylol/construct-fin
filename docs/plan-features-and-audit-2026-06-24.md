# План: доводка аудита + доменные изменения (2026-06-24)

Продолжение большой проверки construct-fin. Две дорожки:
**R** — rollout аудита (62 находки, см. [`audit-phase1-resume.md`](audit-phase1-resume.md)),
**F** — доменные изменения по замечаниям Александра. Формат — как у аудита: проектируем
агентами (несколько независимых вариантов) → адверсариальная верификация против инвариантов
R1–R5 и стандартов учёта → синтез → фиксы. Никакой косметики.

## Контекст

Аудит (Фаза 1) выявил 62 подтверждённых дефекта (11 High). Параллельно Александр дал 8 замечаний
по доменной модели. Часть замечаний усиливает находки аудита (#4 закрывает D4, #9 пересекается с B4),
часть — новая функциональность. Цель этого плана — внедрить и то, и другое одним согласованным
проходом, не переписывая ядро дважды.

## Зафиксированные решения (с Александром)

| # | Решение | Учётное обоснование |
|---|---|---|
| 1 | `color String?` на WarehouseItem, свободный текст | не влияет на учёт |
| 2 | бага нет — COGS корректно расход/неденежный; чинится отображение (D4) | R1/R2 соблюдены |
| 3 | вывести существующее `Order.description` в форму и карточку | — |

| 5 | рассрочка сторонняя — **gross**: ORDER_PAYMENT 100к + VARIABLE_COST 5к, на счёт 95к | полная выручка + стоимость финансирования отдельно |

| 10 | списание = **неденежный убыток** в P&L (по аналогии с COGS) | деньги ушли при закупке; потеря бьёт по прибыли, не по кассе |

## Уточнения (решены 2026-06-24)

- **5a:** сторонняя рассрочка приходит **разово** → одна проводка прихода (95к) + одна комиссия (5к VARIABLE_COST).
- **5d:** экспорт таблицы заказов в Excel — **НЕ нужен** (заказы ведём в приложении). НО нужна **привязка импортной строки выписки к заказу** → строка становится ORDER_PAYMENT (в мастере импорта). Описание текущего Excel-процесса маркировки — ждём от Александра.
- **8a:** нужен **формальный график платежей** (суммы + даты, контроль просрочки) — новая сущность. Рост объёма F2.
- **8b:** выдача = существующий **`finalize`** (там уже списание склада + COGS). Новых статусов не вводим.
- **10c:** причина списания — **свободный текст**.

## Дорожка F — последовательность (по зависимостям)

### F0 — FIFO-партии: фундамент склада 🔴 (делаем первым, максимальная верификация)
Переписать ядро склада с WAVG на партионный учёт.
- **Схема (packages/db):** `StockLot` (item, qty, qtyRemaining, unitCost, supplierId, accountId, sourceType/sourceId, date) + `LotConsumption` (movement, lot, qty, unitCost). Связи к Purchase/Order.
- **warehouse.service / repository:** `applyPurchaseLine` → создаёт лот; `decrementForSale` → списывает лоты FIFO, пишет LotConsumption + возвращает COGS = Σ(qty×unitCost лотов); `restock`/`supplierReturn`/`adjust`/`writeOff` — работа с лотами. Сохранить FOR UPDATE-локи (учесть находку аудита **B4**).
- **COGS/маржа:** `unitCostAtSale` становится фактической себестоимостью списанных лотов.
- **Миграция:** текущий `qty×avgCost` каждой позиции → один лот `OPENING` (поставщик/счёт = null). Обратимость и сверка остатков до/после.
- **Затрагивает:** order.service.finalize, margin.service, отчёты, reconciliation. Аудит-находка B4 закрывается здесь.

### F1 — Маржа по строкам и заказу (#4) + фикс отображения (#2/D4)
Бэкенд считает маржу строки `(unitPrice − unitCost)×qty` и % к выручке, и итог по заказу от `totalAmount`;
отдаёт в DTO заказа. Фронт `orders/page.tsx` только рисует (убрать расчёт в JS number — закрывает **D4**).
Услуга = 100% маржи (R3). Зависит от F0 (источник себестоимости).

### F2 — Выдача + момент COGS + график платежей (#8)
Списание склада и COGS — при **`finalize`** (= выдача), не при оплате. Частичная оплата уже работает
(`PARTIAL`, `addPayment`, остаток). **НОВОЕ: график платежей** — сущность PaymentSchedule (суммы + даты,
контроль просрочки), напр. «часть сейчас, остаток при выдаче». Зависит от F0 (момент COGS).

### F3 — Рассрочка сторонняя gross (#5) + привязка импорта к заказу
Оформление оплаты через стороннюю рассрочку (**разово**): ORDER_PAYMENT на полную сумму (100к) +
автоматический VARIABLE_COST на комиссию (5к, фикс %). **Привязка импортной строки выписки к заказу**
в мастере импорта → строка становится ORDER_PAYMENT. Экспорт заказов в Excel — НЕ нужен. Независимо от F0.

### F4 — Списание WRITE_OFF (#10)
Метод+эндпоинт `writeOff(item, qty, reason)`: списывает лоты FIFO, пишет StockMovement(WRITE_OFF, reason)
и **неденежную** проводку-убыток (новый kind либо переиспользуем механику COGS). Отдельный архив = фильтр
журнала по WRITE_OFF. Зависит от F0.

### F5 — Поставщик + счёт на комплектующее (#9, витрина)
Показ трассировки: на строке заказа и в карточке позиции — из какой партии/закупки взято, поставщик и счёт
оплаты. Питается данными F0. Счета (ИП Каменский, Каменский физ, Антропов физ) — как `Account`.

### F-light — Цвет (#1) + Комментарий (#3)
Независимые, тривиальные. `color String?` + textarea description в UI. Можно пустить параллельно в любой момент.

## Дорожка R — rollout аудита
11 High (см. реестр). Пересечения с F: **B4** (склад) → внутри F0; **D4** (orders JS number) → внутри F1.
Остальные High независимы (TZ/R5 в period/reconciliation, CSV-инъекция, идемпотентность, workspace.deletedAt,
парсер импорта float/разделители, сломанный экспорт format, инвалидация кэша React Query). Medium/Low — после.

## Методология (как в аудите)
Для каждой фазы: workflow с design-агентами (3–5 независимых вариантов под доменную модель) →
adversarial-верификация против R1–R5 и стандартов учёта (refute-by-default, голосование) → синтез в план →
реализация → зелёный прогон (216 unit + 293 integration) + ручная проверка реального кейса. Любое сомнение —
отчёт Александру до фикса.

## Порядок запуска
1. **F0 (FIFO)** — спроектировать первым (design-workflow), отдельно от всего: ошибка ломает деньги во всех отчётах.
2. Параллельно — F-light и независимые High аудита.
3. После F0 — F1, F2, F4, F5; затем F3.

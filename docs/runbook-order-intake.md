# Протокол: занесение архива клиента (клиент → заказ → чеки → сведение с выпиской)

Черновик-заготовка будущего скилла/workflow. Пишется **по ходу живой работы** в UI,
а не по памяти: каждый шаг фиксируется с фактическими значениями полей и фактическим
результатом. Вопросы, которые пришлось задать владельцу, — это будущие **параметры**
функции; развилки — её **ветвления**.

Правило записи: если шаг не сработал с первого раза, пишем и неудачную попытку тоже.
Отлаженная процедура без граблей бесполезна — грабли и есть самое ценное.

## Единица работы

Один архив = один покупатель = один заказ. Внутри архива: спецификация (позиции и цены
продажи), чеки закупки (себестоимость), иногда текстовые файлы с договорённостями.

## Принятые решения (действуют на все архивы)

| Решение | Значение | Почему |
|---|---|---|
| Позиции чеков | сразу в заказ (`target: ORDER`), склад не трогаем | закупка адресная, под конкретного клиента |
| Деньги чека | привязка к существующей операции (`mode: link`) | иначе расход задвоится: он уже есть строкой выписки |
| Вложения | к заказу (к клиенту нельзя — нет такой связи) | `Attachment` цепляется к `orderId`/`transactionId` |
| Загрузка файлов | кликает владелец | у панели агента нет инструмента выбора файла |
| Дата закрытия заказа | **дата денег** (приход в банке, для наличных — дата получения) | выручка признаётся по `closedAt`; дату отгрузки часто не вспомнить, а дата денег есть всегда |
| Карты ВБ | их три: Каменск …8975, Антропов …4510, Дерябин | закупки уходили со всех трёх |
| Счёт «ВБ Дерябин» | заведён у Каменского 02.08 | закупки с него нужны в себестоимости |
| Операции Дерябина | часть относится к пространству «ИП Дерябин» — отсеивать вручную при разборе | одна карта обслуживает два ИП |
| Выписки карт ВБ | есть только по Каменску (залита); по Антропову и Дерябину **не будет** | закупки с них не имеют денежного следа |
| Закупка без денежного следа | решается по каждому архиву: завести расход вручную на счёт карты либо оставить заказ без этой части себестоимости | владелец выбирает, глядя на сумму |
| **Строки закупок в выписке** | проводить **как есть**, категорией «Закупка товара», без привязки к заказу | один платёж картой покрывает чеки нескольких заказов; себестоимость заказа берётся из его позиций и от способа оплаты не зависит |
| **Ручные закупки** | заводить **только** для карт без выписки (ВБ Дерябин, ВБ Антропов) | иначе те же деньги лягут в расходы дважды: строкой банка и ручной операцией |
| Карта «Вася» из заметок | это счёт **ВБ Дерябин** | решение владельца 09.08 |
| Счёт «Иное» | временный отстойник для расходов, чей след в выписке пока не опознан | это не реальный счёт: деньги ушли с Альфы, строку предстоит найти и перенести операцию туда |

**Пространство «ИП Дерябин»** (создано 21.06, пустое) владелец решил вести параллельно —
часть будущих архивов пойдёт туда.

### Грабли и находки (переносятся на все архивы)

1. **Имена файлов в zip приходят в cp866/cp1251** — штатный `unzip` спотыкается
   («Illegal byte sequence»). Распаковывать с перекодировкой: `encode('cp437').decode('cp866')`
   при снятом UTF-8-флаге.
2. **Один чек может обслуживать несколько заказов.** В чеке WB четыре позиции на
   81 614, а к этому клиенту относятся только две на 43 128 — второй процессор и
   RTX 5060 (без Ti) ушли не сюда.
3. **Какие позиции чьи — сказано в текстовой заметке архива.** Здесь: «Проц 10545,
   Видеокарта 32583». Без неё разложить чек по заказам невозможно.
4. **Закупка может быть оплачена с карты вне контура учёта.** Проверять по выписке
   ДО заведения заказа: если расхода нет, спрашивать владельца, как проводить.
5. **Спецификация содержит позиции, которых нет в чеках** — вентиляторы (5 шт.),
   рамка процессора, держатель видеокарты, кастомные элементы. Источник их
   себестоимости отдельный вопрос (склад или не учитываем).

**Заказ:** от 30.06.2026, «ПК CONSTRUCTPC (Ryzen 5 7500F; RTX 5060 Ti)», **148 156 ₽**,

**Приход:** 01.07.2026 на 148 156 ₽ через СБП-эквайринг Альфы. Сумма сошлась со
спецификацией точно.

**Себестоимость — 108 682 ₽:**

| Источник | Позиции | Сумма | След в выписке |
|---|---|---:|---|
| WB (карта «Илья» = ВБ Каменск) | ОЗУ 22 845 + видеокарта 34 357 + процессор 8 817 | 66 019 | ВБ Каменск, 01.07 |
| WB (карта «Саня» = ВБ Антропов) | диск ADATA LEGEND 860 | 17 865 | **нет** |
| ДНС | матплата 9 299 + СЖО 6 199 | 15 498 | Альфа, 06.07 |
| Онлайн Трейд | БП 5 410 + корпус 3 890 | 9 300 | Альфа, 02.07 |

Валовая маржа **39 474 ₽ (26,6 %)**.

### Находки

6. **Клиент мог быть заведён раньше** — проверять справочник до создания.
7. **Имена в заметке — это карты, а не люди.** «Илья» = ВБ Каменск, «Саня» = ВБ Антропов
   (Александр Антропов). Сопоставлять по сумме с выпиской, а не по имени.
8. **Сводный чек WB покрывает много заказов.** Чек №658 — 16 позиций на 314 415 ₽, из них
   к архиву относятся три. Читать чек целиком (у него 5 страниц) и брать позиции по заметке.
9. **Цены продажи по позициям в спецификации нет** — только итог. Если заказ заводится по
   компонентам, цену раскидывают пропорционально себестоимости, последняя строка добирает
   остаток до копейки.
10. **Группа категории («Закупка товара» = COGS) задваивала себестоимость.** ОПиУ исключает
    операции вида COGS и берёт себестоимость из заказов, но обычная операция с категорией
    в группе COGS не исключается. Нужна группа «Закупки» (`PURCHASES`). Поля в интерфейсе
    не было — добавлено (PR #133), заодно поймана и исправлена регрессия вёрстки (#134).
11. **«Возврат выручки» — расход с группой «Выручка».** Оказалось, что это верная пара:
    ОПиУ считает выручку как нетто (доход бакета минус его расход), то есть возврат её
    уменьшает. Запрещала её проверка на сервере, из-за чего категория залипла и не
    сохранялась вовсе. Пара разрешена явно (PR #136).
12. **Дата закрытия заказа была зашита на «сегодня».** `closedAt` и дата COGS-проводки
    брались как `new Date()`, API дату не принимал. Для архивов это уводило выручку и
    себестоимость в текущий месяц, оставляя в месяце сделки одни закупки. Исправлено
    (PR #135): дата отгрузки спрашивается при закрытии и датирует обе записи.
13. **Приход клиента через эквайринг содержит название сборки** — в описании строки
    видно «ПК CONSTRUCTPC (AMD Ryzen 5 7500F…)». Помогает опознать платёж.
14. **Две кнопки «Закрыть заказ» на одном экране** — в футере карточки и в диалоге
    подтверждения. Промахнуться легко: диалог закрывается без сохранения, и кажется,
    что нажатие «не сработало». Кандидат на переименование кнопки в диалоге.
15. **Правило закрытия — по дате денег** (решение владельца 09.08). Не нужно гадать
    про отгрузку: берём дату прихода в банке, для наличных — дату получения.
16. **Excel-реестр владельца — только список «кто был»**. Суммы в нём могут расходиться
    с документами (встречаются убыточные заказы, дубли, свалка дат на конец месяца).
    Истина: спецификация + чеки + выписка.

17. **Эквайринг Альфы устроен двумя разными способами** — это главная находка 09.08,
    без неё платежи не находятся, а заказы висят недоплаченными.

    **СБП** — приход и комиссия приходят парой строк с одинаковым идентификатором
    `C3…`: `+264 757,15` и `−794,27` (оба `C300708260699420`), ставка ~0,3 %. Комиссию
    просто разносим расходом, оплата заказа равна сумме прихода.

    **Торговый эквайринг по картам** — `Возм 667302152487 … Р.09072026 К.4837.50 в т.ч.
    НДС 872.34`: зачисление уже за вычетом комиссии, отдельной строки на неё **нет**
    (проверено поиском по всем трём вкладкам), ставка ~3,17 %. Клиент заплатил
    `зачислено + К.`. Сверка на трёх случаях: 63 285,82+2 073,18 = 65 359 (предоплата
    Касьянова), 147 668,50+4 837,50 = 152 506 (его же доплата), 344 920,70+11 299,30 =
    356 220 (Кузнецов). С 09.08 такие строки расщепляются приложением автоматически
    (PR #138): оплата по брутто + расход «Банковские услуги» той же датой.

18. **Платёж клиента ищется не по сумме из документов.** При эквайринге в выписке лежит
    нетто, поэтому поиск по «152 506» не находит ничего. Работают: фамилия клиента (если
    банк положил её в контрагента — так нашёлся Мингазов), конфигурация сборки из
    назначения («7800X3D»), фрагмент даты расчёта («Р.2506»).

19. **Одна строка выписки покрывает закупки нескольких заказов.** 19.07 в ДНС три
    списания (45 347, 77 696, 203 294), а чек архива — на 13 598: он внутри одного из них.
    Поэтому строки проводим целиком как «Закупка товара» без привязки к заказу, а
    себестоимость заказа берём из его позиций.

20. **Форма «Принять оплату» в карточке заказа не имеет поля даты** — оплата встаёт
    сегодняшним числом. Для архивов задним числом это искажает месяц; пока обходим тем,
    что оплаты привязываем строками выписки (там дата берётся из строки).

21. **Заведение ускоряется в разы, если не кликать по одному полю.** Первый архив занял
    52 минуты, второй — 9. Разница только в способе: добавление строк позиций и
    заполнение полей делаются пачкой, а не по одному обращению к браузеру.

### Порядок шагов, отработанный на архиве 2

1. Проверить, есть ли клиент в справочнике (мог быть заведён раньше).
2. Прочитать спецификацию (позиции, итог) и заметку (какие позиции чека чьи).
3. Прочитать чеки, собрать себестоимость; сверить каждую закупку с выпиской по
   сумме — понять, что есть в контуре, а что оплачено картой без выписки.
4. Найти приход клиента, сверить с итогом спецификации.
5. Завести заказ: позиции с закупочными ценами, цена продажи распределена
   пропорционально (последняя строка добирает остаток до копейки). График оплаты —
   «Без оплаты», реальный приход привязывается отдельно.
6. Провести строки-закупки во «Входящих» категорией группы «Закупки».
7. Закупку без денежного следа завести вручную на счёт соответствующей карты.
8. Привязать приход «К заказу» — заказ становится оплаченным.
9. Закрыть заказ датой отгрузки.

Первая проверка мастера (#166 спецификация, #167 цены из чеков) не на одной папке, а на

### Что за популяция

Архивы лежат в **трёх корневых папках облака**, а не в одной. Это важнее всех остальных
цифр прогона: учёт до сих пор видел только первую.

| Корень | Папок клиентов | Сумма по спецификациям |
|---|---:|---:|
| CONSTRUCT | 128 | 20 323 255 ₽ |
| APEX | 44 | 14 959 903 ₽ |
| Сервисные сборки | 10 | 1 566 313 ₽ |
| **Всего** | **182** | **36 849 471 ₽** |

Остальные папки облака к учёту не относятся: «Контент» — маркетинговые съёмки по месяцам,

### Разбор спецификаций: было 62 %, стало 92 %

Первый прогон дал 62,3 % файлов без единого предупреждения. Причины нашлись две, обе
массовые, и обе исправлены:

1. **Спецификация без единой таблицы** — 22 файла. Часть шаблонов свёрстана абзацами:
   подпись и значение соседними строками, позиции списком после «Техническая
   спецификация:». Парсер читал только таблицы и не видел вообще ничего.
   Лечится приведением абзацев к той же форме (`paragraphsToTables`), причём с обязательной
   границей по «Гарантийному обслуживанию»: ниже идёт текст договора, и его строки вида
   «Условия гарантии: …» по форме неотличимы от позиций.
2. **Телефон и дата слитно** — 25 файлов: «89103995527От 18 января 2026 г.». Разделитель
   требовал пробела перед «от».
3. Мелочь: у одного клиента в номере два телефона через «/» — в заказ идёт первый.

После правок 92 % (127 из 138). На двух других корнях, увиденных позже, тот же парсер сразу
дал 97,8 % (APEX, 44 из 45) и 90,9 % (сервисные сборки, 10 из 11) — остаток там это доборные
документы. Весь остаток объясним: 10 доборных документов на одну-две
позиции, 4 посторонних файла в папках (не спецификации) и один заказ с опечаткой в номере
(12 цифр вместо 11) — это данные, а не разбор.

### Подстановка цен из чеков: 78 % позиций, ноль ложных

Прогон по выборке из 15 папок (эталонные с руками сверенной себестоимостью, целевые
июньские и августовские, «злые» — Ozon, скан, сводный чек): 126 позиций, 98 получили цену
автоматически.

Найденные и исправленные ошибки сопоставления — обе молча искажали деньги:

4. **«RTX 5060» подменяла «RTX 5060 Ti»**: обе строки лежат в одном сводном чеке WB, цена
   расходится на пять тысяч. Теперь суффиксы `ti/super/xt/xtx` при одностороннем наличии
   штрафуются, причём распознаётся и слитное написание «5060TI». Список нарочно короткий:
   «MAX», «PLUS», «LITE» бывают частью полного имени и дают ложные отказы.
5. **Объём считался моделью**: «16Гб» весила как артикул, и память цеплялась к первой
   попавшейся строке с тем же объёмом. Токены вида «16гб», «750w», «5600мгц» больше не
   модель.

Эталонная сверка после правок: себестоимость архива 1 совпала с посчитанной руками **до
рубля** (76 443 ₽, 8 позиций из 9 — девятая со склада, её в чеках нет). Архив 3 дал
154 280 ₽; недостающие 7 283 ₽ — это чек Ozon (нечитаемый источник) и корпус, чьё название
в чеке и в спецификации не пересекается ни одним словом. Ложных цен на эталонах нет.

### Грабли (продолжение общего списка)

22. **Страница заказа Онлайн Трейда: имена и цены сшиваются по порядку, и порядок не
    гарантирован.** Названия печатаются отдельной секцией от таблицы, и в одном из живых
    файлов первое имя относилось к последней строке таблицы. Ошибка тихая: цена встанет
    не тому товару. Сейчас парсер режет секцию по якорю «схема проезда» (есть в большинстве
    файлов) и начинает название только с русского слова с большой буквы — перенос внутри
    названия идёт латиницей, цифрой или строчной буквой. При расхождении счётчиков строк и
    имён выдаётся предупреждение — **это тот случай, когда цены надо сверить глазами**.
23. **Название без кода модели в скобках склеивалось со следующим**, и последняя позиция
    оставалась безымянной («Позиция 4») — то есть без цены. После правки архив 1 добирает
    корпус и сходится с эталоном.
24. **Сводный чек содержит товары нескольких заказов** — лишние строки после подстановки
    показываются списком. Их и надо читать: там видно, что не легло и почему.
25. Позиции спецификации без чека (вентиляторы, рамки, склад) не получат цену никогда —
    это не дефект разбора, а отсутствующий источник.

### Как повторить прогон

```
SPEC_DIR=<папка со спецификациями> pnpm --filter @construct/api test spec-parser.manual
SPEC_STRICT=1 SPEC_DIR=<...>   # строгий режим: канарейка «шаблон не менялся»
ARCHIVE_DIR=<папка с папками архивов> pnpm --filter @construct/api test costs-match.manual
```

Первый печатает сводку по популяции и классы предупреждений с количествами, второй —
разбор каждого архива: что сопоставилось, с каким обоснованием, какие строки чеков остались
лишними и какие файлы не опознаны. Оба ничего не пишут в базу.

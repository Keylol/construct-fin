## 4. ⚠️ ГЛАВНОЕ ДЛЯ ПЕРЕНОСА ДАННЫХ — анализ риска потери

Полный разбор (он уже обсуждался, держать в голове в новом чате):

из строк `Transaction` — пока живы транзакции, жив отчёт.

**3 реальных вектора риска:**
1. 🔴 **Бэкап был только на VPS** — закрыто (теперь pull на Mac + restore-тест). Перед ЛЮБОЙ схемной миграцией — снапшот.
2. 🟠 **Удаление enum-значений требует ремапа, а не дропа.** Если завести данные под значениями, которые мы убираем (DRAFT-заказ, бакет NON_OP, счёт CARD), миграция обязана сперва переназначить строки.
3. 🟡 Дропаемые таблицы (`RecurringRule`, `AccountingPeriod`) бизнес-данных не содержат → безопасно. `IdempotencyKey` — **решено оставить** (см. п.5).

**Правило при заведении данных, чтобы рефакторинг был без ремапа:**
- заказы создавать сразу **OPEN** (не DRAFT);
- счета — тип **BANK/CASH** (не CARD);
- категории не вешать на **NON_OP** (бакет CAPITAL — **оставляем**, использовать можно; допустимы REVENUE/COGS/FIXED/VARIABLE/TAX/CAPITAL/OTHER).

**Регламент миграций (на что я подписался):** pg_dump перед каждой схемной
миграцией → деструктив только двухшагово (ремап → потом дроп) → прогон на копии
БД до прода → soft-delete оставляем.

soft-delete везде; **бакет CategoryBucket.CAPITAL** (см. ниже); **IdempotencyKey** (см. ниже).

**2 противоречия — РЕШЕНЫ 2026-05-30 (план ревизован):**
1. **Бакеты NON_OP/CAPITAL.** Отчёты классифицируют операцию по `category.bucket`,
   а не по `transaction.kind` (единственное исключение — агрегат `kind:'COGS'` в
   `pnl.service.ts:127`). Бакет `CAPITAL` — единственное, что исключает вложения/
   изъятия собственника из операционного P&L (`pnl.service.ts:190`:
   `operatingIncome = income − capitalIncome`). Поэтому:
   - `NON_OP` → **убираем** (remap → `OTHER`). В P&L NON_OP считается ровно как
     обычный расход/доход — релейбл на OTHER не меняет ни одной цифры. Безопасно.
   - `CAPITAL` → **оставляем**. Удаление бакета без переноса логики на kind
     затащило бы капитал собственника в операционную прибыль. Kind'ы
     `CAPITAL_IN`/`CAPITAL_OUT`/`NON_OP` остаются (отчёты их и так не читают).
2. **IdempotencyKey — оставляем.** Интерсептор глобальный, но пассивный
   (`idempotency.interceptor.ts:41`: нет заголовка → no-op) — нулевая
   эксплуатационная цена. Клиент шлёт ключ только на дорогих мутациях (оплата
   заказа, finalize, создание закупки, склад). Это ровно те операции, где дубль
   при double-tap/ретрае в Mini App задваивает деньги или портит `avgCost`
   (→ COGS поедет). Снос бил бы по корректности данных (топ-оценка ~8.5) ради
   удаления одной таблицы + пассивного интерсептора. Не стоит.

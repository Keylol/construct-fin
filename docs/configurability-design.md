# Дизайн: конфигурируемость без разработчиков

Цель — дать владельцу настраивать поведение приложения из UI, без правки кода.
Опорный принцип: всё, что настраивается, привязано к трём точкам жизни операции —
**ввод → классификация → отчёт** — поверх неизменного транзакционного ядра.

Решения Александра (2026-07-04): нужны все 4 блока; движок правил — на
**фиксированных условиях** (безопасно, предсказуемо).

## Тир-модель безопасности (граница «конфиг vs код»)

| Тир | Что конфигурируется | Почему безопасно |
|---|---|---|
| **1. Свободно** | категории, правила класс-ции, шаблоны, настройки пространства | данные/маршрутизация — деньги не портят |
| **2. С ограждениями** | kind→бакет отчёта, денежный/неденежный, авто-комиссии | влияет на отчёты, не на леджер — нужна валидация конфига |
| **3. Только код** | Decimal-арифметика, FIFO, атомарность UoW, создание Transaction | config-ошибка = необратимая порча денег |

Правило: **конфигурируемые данные + ограниченный движок правил из фиксированных
словарей**. НЕ произвольный скриптинг/DSL — им можно испортить деньги.

## Блок 1 — Движок правил «условие → действие» (центр)

Обобщение существующего `CategoryRule` (keyword→категория). Новая сущность `Rule`.

**Условия (фиксированный словарь, любое сочетание И):**
- контрагент = / счёт = / вид (kind) = / тип (доход/расход)
- сумма в диапазоне [min, max]
- слово в описании (contains)
- источник (импорт / ручной ввод / конкретный банк-парсер)

**Действия (фиксированный словарь):**
- назначить категорию / счёт / контрагента
- пометить как перевод (кандидат)
- добавить авто-комиссию N% отдельной строкой (Тир 2 — с валидацией)
- применить шаблон (см. Блок 2)

**Точки применения:** мастер импорта (как сейчас CategoryRule), форма ручного
ввода (подсказка/автозаполнение), опц. создание заказа/закупки.

**Модель:** `Rule { workspaceId, priority, enabled, conditions[], actions[], appliesTo }`.
Условия/действия — JSON из фиксированных типов (не код). Движок — чистая функция
`applyRules(context, rules) → suggestions`, тестируемая изолированно (как matcher.ts).

**Прозрачность:** правило только ПРЕДЛАГАЕТ (подсветка «применено правило X»),
пользователь подтверждает — деньги не двигаются автоматически без ведома.

## Блок 2 — Шаблоны операций

`OperationTemplate { name, type, kind?, categoryId?, accountId?, counterpartyId?, amount?, note? }`.
Быстрый ввод частых операций («Аренда», «Зарплата Иванову») одной кнопкой.
Может вызываться действием правила. Чистые данные — Тир 1.

## Блок 3 — Настройки пространства

`WorkspaceSettings { timezone, currencyLabel, displayRounding, fiscalYearStart, dashboardWidgets[] }`.
Сейчас зашито (UTC+5, ₽, half-up). Вынести в конфиг с дефолтами = текущие значения.
Тир 1 (отображение) кроме fiscalYearStart (влияет на периоды — Тир 2, валидация).
**Важно:** бизнес-TZ для границ периодов остаётся детерминированным per-workspace,
не per-браузер (иначе отчёты «поплывут» — см. council K7/IJ).

## Блок 4 — Конструктор отчётов/бакетов (Тир 2)

Заменяет зашитый `bucketForSystemKind`. Таблица настроек
`BucketMapping { kind → bucket, isCash }` + определения агрегатов
(`grossProfit = какие бакеты`, `operating net = какие`).
**Ограждения:** валидатор конфига не даёт (а) оставить kind без бакета,
(б) пометить ORDER_PAYMENT неденежным, (в) сломать сходимость net. Дефолт =
текущий код-маппинг. **Зависит от Волны 3** (сначала починить формулы grossProfit/
net, потом делать их конфигурируемыми — иначе конфиг унаследует баги).

## Порядок реализации (предложение)

1. **Блок 1 (движок правил)** — максимальная ценность, есть прототип (matcher),
   Тир 1. Расширить схему Rule + движок + UI-конструктор правил + применение в импорте/вводе.
2. **Блок 2 (шаблоны)** — дёшево, самостоятельно, усиливает Блок 1.
3. **Блок 3 (настройки)** — вынести зашитое в WorkspaceSettings.
4. **Блок 4 (конструктор отчётов)** — ПОСЛЕ Волны 3 (починки формул), Тир 2 с валидацией.

## Связь с транзакционным ядром

Ничего из этого не трогает создание Transaction, Decimal, FIFO, UoW. Движок
работает НА ВХОДЕ (что подставить в форму/импорт) и в КЛАССИФИКАЦИИ (категория/
бакет), но саму запись денег делает то же неизменное ядро. Отчёты читают конфиг
маппинга, но суммируют те же Transaction. Это и есть безопасная граница.

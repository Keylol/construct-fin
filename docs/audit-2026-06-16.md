## Трек A — Точность кэш-флоу и отчётов (ПРИОРИТЕT №1, дёшево)

Каждый день владелец смотрит на эти цифры, и они врут. Все фиксы — точечные, под существующими integration-тестами.

- **A1 [CRIT]** `summary()` задваивает переводы. `transaction.service.ts:234` — добавить `kind: { notIn: ['TRANSFER_IN','TRANSFER_OUT'] }` в `where`. Перевод между своими счетами раздувает income и expense на главном экране.
- **A2 [HIGH]** breakdown по категориям/контрагентам задваивает переводы. `reports/breakdown.service.ts:76` (`buildWhere`) — тот же `notIn`. Сейчас переводы валятся в «Без категории» и пачкают доли.
- **A3 [HIGH]** торговая выручка и закупки не попадают в бакеты REVENUE/COGS. `reports/pnl.service.ts:167` — маппинг по kind: `ORDER_PAYMENT→REVENUE`, `PURCHASE→COGS`, `CAPITAL_IN→CAPITAL`. Сейчас вся выручка продаж лежит в OTHER → разбивка P&L по бакетам бесполезна.
- **A4 [MED]** маржа не вычитает RMA-возвраты. `reports/margin.service.ts:101` — считать по `(qty − returnedQty)`. После возврата отчёт завышает прибыль позиции.
- **A5 [MED]** ручной COGS датируется `new Date()` finalize, а не `closedAt`. `orders/order.service.ts:427` — COGS уезжает не в тот период при закрытии задним числом.
- **A6 [MED]** возврат поставщику оформлен как доход (kind=OTHER), а не contra-COGS. `warehouse/warehouse.service.ts:294` — отдельный kind `SUPPLIER_REFUND` + бакетизация (нетто верный, но breakdown по поставщикам вводит в заблуждение).

## Трек B — Корректность денежных флоу (бэкенд, money-critical)

- **B1 [CRIT]** `addPayment` не проверяет, что счёт принадлежит workspace. `orders/order.service.ts:170` — добавить `assertAccount(workspaceId, dto.accountId)` (как в `returnItem`). Сейчас можно постнуть платёж на чужой счёт → утечка изоляции + порча кэшфлоу.
- **B2 [HIGH]** order TOCTOU: заказ читается ДО транзакции, мутируется по устаревшему снапшоту. `orders/order.service.ts` (ship/finalize/return/cancel) — переносить чтение внутрь `uow.run` + лочить строку заказа (или условный `updateMany` с guard по `shippedQty`). Конкурентные ship+finalize дают oversell/double-ship.
- **B3 [CRIT]** idempotency не разделяет транзакцию с домен-мутацией. `common/idempotency.interceptor.ts:84` — при краше между commit домена и `complete()` операция применяется дважды / висит 409 на 24ч. Класть idem-строку в ту же `$transaction`.
- **B4 [HIGH]** order create/update не валидируют `clientId`/`warehouseItemId` по workspace. `orders/order.service.ts:52` — добавить проверки (как `validateRefs` в транзакциях).
- **B5 [HIGH]** `nextNumber` ломается на 10000 (лексикографическая сортировка строки) + гонка. `orders/order.repository.ts:66` — числовая последовательность через атомарный счётчик.
- **B6 [MED]** `supplierReturn`: деление refund на returnQty без guard `>0` (500) + WAVG может уйти в минус. `warehouse/warehouse.service.ts:294`, `common/wavg.ts:73`.

## Трек C — Telegram Mini App на фронте (заявлен в ТЗ, на v6 НЕ реализован)

- **C1 [CRIT]** реализовать авто-логин Mini App + Login Widget. `apps/web/src/app/login/page.tsx` — при наличии `window.Telegram.WebApp.initData` дёргать `POST /auth/telegram/miniapp` → `/dashboard`; пароль оставить fallback. Эндпоинты на бэке живые, фронт их не вызывает. **Решить с владельцем: нужен ли Mini App-канал сейчас.**
- **C2 [HIGH]** нет обработки 401 и нет кнопки выхода. `lib/api.ts:42` — на 401 редирект на `/login`; добавить logout (бэк `POST /auth/logout` есть).
- **C3 [HIGH]** деньги считаются float на клиенте. `packages/shared/src/money.ts`, формы заказов/склада — убрать `String(Number(...))` round-trip, превью считать в копейках.

## Трек D — Безопасность входа

- **D1 [HIGH]** 24ч replay-окно `initData`. `auth/telegram-verify.ts:16` — срезать до ~300–900с.
- **D2 [HIGH]** throttle-бакет спуфится через `X-Forwarded-For`. `deploy/nginx/construct-v6.conf:49` ставит `$proxy_add_x_forwarded_for` (append) + `trustProxy:true` (`main.ts:27`) → brute-force пароля. Чинить: nginx `proxy_set_header X-Forwarded-For $remote_addr` или `trustProxy: 1`.

## Трек E — Эксплуатация (катастрофоустойчивость — хостер уже банкротился)

- **E1 [CRIT]** бэкап без off-site и без restore-теста; лежит на том же VPS, что и БД. `deploy/docker-compose.prod.yml:85` — rclone/rsync дампов на S3/B2 + периодический restore-в-пустую-БД (healthchecks.io dead-man-switch).
- **E2 [CRIT]** деплой без отката. `.github/workflows/deploy.yml:91` — тегировать прежний sha, при красном health/smoke авто-откат; миграции до переключения трафика.
- **E3 [HIGH]** мониторинг/алерты только в инструкции, не подтверждены живыми; Sentry нет. Поднять uptime-пинг с алертом в Telegram + error-tracking.
- **E4 [HIGH]** фронт — 0 тестов, e2e нет. Playwright smoke на 3 флоу (логин → транзакция → отчёт сходится).

## Трек F — Целостность БД (строго аддитивные миграции)

- **F1 [HIGH]** drift partial-unique индексов держится на памяти разработчика. CI-guard: `grep` сгенерённой миграции на `DROP INDEX .*_active_key` → fail.
- **F2 [HIGH]** нет partial-unique на естественных ключах справочников (`Account` name, `Category`, `Counterparty` inn) → дубли пачкают отчёты. Добавить после дедупа данных.
- **F3 [MED]** ни одного CHECK-инварианта. Добавить `CHECK` на `qty>0`, `shippedQty<=qty`, `returnedQty<=qty`, `WarehouseItem.qty>=0`, `avgCost>=0` и т.п.

## Рекомендуемый порядок

1. **Трек A** — приоритет владельца (точность кэшфлоу), дёшево, высокая ценность, под тестами. Один-два PR.
2. **Трек B** — money-critical корректность (гонки/утечки в денежных путях). B1 — тривиальный и опасный, делать сразу.
3. **Трек E (E1/E2)** — катастрофоустойчивость; хостер уже банкротился, бэкап и откат — страховка.
4. **Трек D** — периметр входа (быстро, конфиг + пара строк).
5. **Трек F** — целостность БД (аккуратные аддитивные миграции).
6. **Трек C** — зависит от решения по Mini App-каналу.

**Правила прежнего плана сохраняются:** каждая фаза — отдельный PR → зелёный CI → Haiku-ревью → мёрж; в `v6` не пушить напрямую; миграции только аддитивные и только в `v6`; после миграции — проверка факта БД.

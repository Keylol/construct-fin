# Ф2 — Альфа-Бизнес API (выписка по расчётному счёту)

Разведка контракта и реализация адаптера, 2026-07-26. Источник:
[developers.alfabank.ru](https://developers.alfabank.ru/products/alfa-api).

## Что выбрано и почему

У Альфы **два** метода выписки, оба доступны в песочнице и на проме:

| Метод | Путь | Авторизация | Особенности |
|---|---|---|---|
| Открытый банкинг | `/jp/open-banking/v1.3/accounts/{accountId}/statements` | только Bearer (OAuth) | стандарт ЦБ 1.3.3le, нужен `accountId` из `accounts-ob`, ИНН лежит глубоко в `Debtor.Agent.OrganizationIdentification` |
| **Выписка (выбран)** | **`/v1/statement/transactions`** | **Bearer или `ApiKey`** | принимает **номер счёта** напрямую, плоские поля `payerInn`/`payeeInn`/`paymentPurpose`, до 1000 операций на страницу |

Взят второй: **`Authorization: ApiKey {key}`** не требует интерактивного входа
пользователя, поэтому ежечасный крон работает без участия владельца. Bearer по
Authorization Code Flow означал бы браузерный вход в Alfa ID и заботу о
refresh-токене (180 дней) — для фонового синка это лишняя точка отказа.

API Key выпускается один раз на Портале разработчика, действует бессрочно, но
**автоматически отзывается, если запросов не было 30 дней** (наш синк ходит
каждый час — не проблема).

## Ограничения банка, вокруг которых построен адаптер

1. **Глубина выписки — ровно один календарный день.** Отсюда цикл по дням в
   `AlfaAdapter.fetchStatement`, а не диапазон.
2. **История — не ранее 5 лет от 1 января текущего года.** Дата клампится
   (`historyFloor`).
3. **mTLS обязателен** — и в песочнице, и на проме. Без клиентского сертификата
   соединение обрывается на TLS-рукопожатии.
4. **Пагинация** — `page`, наличие следующей страницы видно по `_links[rel=next]`.
5. Признака **АУСН в ответе нет** → `ausnMark` остаётся `null`, сверка налога
   (Ф4) идёт по fallback-пути из генплана, а не по этому API.

## Как это работает у нас

```
крон (раз в час) / кнопка «Обновить»
  → SyncService.syncConnection
     → AlfaAdapter.fetchStatement({ apiKey, cursor, accountNumber, connectedAt })
        → цикл по дням: GET {base}/v1/statement/transactions?accountNumber=&statementDate=&page=
        → маппинг DEBIT→EXPENSE / CREDIT→INCOME, контрагент = «другая сторона»
     → upsert BankStatementLine по (connectionId, externalId)
     → Rule-движок → авто-проводка либо строка в Inbox
```

- **Курсор** (`syncCursor`) — последний **полностью закрытый** день. Текущий день
  перезапрашивается на каждом синке (операции по нему ещё доезжают); дубли
  невозможны — идемпотентность по `(connectionId, externalId)`.
- **Первый синк** начинается с даты создания подключения: история до подключения
  уже занесена руками (решение №15 генплана).
- **За один синк** берётся не больше 31 дня; остаток догоняется следующим
  проходом (в лог пишется, сколько отложено — молча выписку не режем).
- **Смена номера счёта** в UI сбрасывает курсор: другой счёт — другой источник.

Файлы: [`alfa.adapter.ts`](../apps/api/src/integrations/adapters/alfa.adapter.ts),
[`alfa-transport.ts`](../apps/api/src/integrations/adapters/alfa-transport.ts)
(mTLS на `node:https`, без новых зависимостей),
тесты — `alfa.adapter.test.ts` и блок «SyncService + AlfaAdapter» в
`sync.integration.test.ts`.

## Настройка

## Сертификат живёт в подключении, а не на сервере

Банк выдаёт клиентский сертификат **на компанию по договору**, поэтому у двух
пространств (разные ИП) сертификаты разные. Держать один общий в env сервера
нельзя: второе пространство пошло бы в банк под чужим сертификатом и получило
отказ.

Пара cert+key (и пароль, если он есть) загружается в форме подключения и
хранится в `IntegrationConnection.tlsCredentialEnc` — зашифрованной тем же
мастер-ключом, что и API Key. Наружу отдаются только публичные метаданные:
отпечаток SHA-256 и срок действия (UI предупреждает за 30 дней до истечения —
просроченный сертификат означает молча вставший синк). Закрытый ключ не
попадает ни в ответы API, ни в аудит, ни в логи.

Транспорт держит **агент на сертификат** (ключ кэша — хеш пары), а не один на
процесс: TLS-рукопожатие на каждый день выписки было бы дорого, а после ротации
старый агент не переиспользуется.

`ALFA_TLS_*` в env остаются **запасным вариантом** — для подключений, заведённых
до появления загрузки в интерфейсе. Если у подключения свой сертификат, env
игнорируется.

Отдельная тонкость: вне прода реальный адаптер включается, только если
`ALFA_TLS_*` заданы явно. Иначе он вытеснил бы `FakeBankAdapter`, на котором
держатся демо и интеграционные тесты полного цикла.

### 1. Песочница (то, что можно сделать сейчас)

Альфа прислала `test_cert.zip` и тестовые client_id для H2H и B2B.

1. **Пароль от архива** — запросить на `alfa_api@alfabank.ru` (в письме прямо
   сказано, что пароль выдаёт персональный менеджер). Без него сертификат не
   распаковать.
2. Распаковать архив. Из него понадобятся два файла:
   - `sandbox_cert_2026.cer` — клиентский сертификат;
   - `sandbox_key_2026.key` — закрытый ключ.
3. **Выпустить API Key** (внутренний, H2H) на Портале разработчика — раздел
   «Управление API Key».
4. Прописать адрес песочницы в `.env.production` (или локальном `.env`):
   ```
   ALFA_API_BASE_URL=https://sandbox.alfabank.ru/api/jp
   ```
5. В приложении: **Интеграции → Подключить банк** → Альфа-Банк, счёт, номер
   расчётного счёта, API Key и **загрузить сертификат с ключом прямо в форме**.
   Тестовые счета песочницы: `40702810102300000001`, `…0002`, `…0003`,
   `40702978902300000004` (валютный).

Если банк выдал `.p12`/`.pfx` вместо пары файлов, пару достают из контейнера:
```bash
openssl pkcs12 -in cert.p12 -clcerts -nokeys -out client.cer
openssl pkcs12 -in cert.p12 -nocerts -nodes -out client.key
```

Проверка живости — кнопка «Обновить» на подключении: строки должны появиться во
«Входящих».

### 2. Пром

То же самое, но:
- `ALFA_API_BASE_URL` не задаётся (по умолчанию `https://baas.alfabank.ru/api/jp`);
- сертификат и API Key — боевые, из Портала разработчика по своей компании;
- на сервере обязателен `INTEGRATION_MASTER_KEY` (иначе весь модуль интеграций
  отвечает 503 — секреты негде шифровать).

Второе пространство (другой ИП, свой договор с банком) настраивается так же:
подключение в своём пространстве со своим API Key и своим сертификатом. Ничего
в env добавлять не нужно — пространства не пересекаются ни данными, ни
сертификатами.

Отдельно: для корректной работы TLS **нужны сертификаты Минцифры** на стороне
клиента. Если банк сменит УЦ и цепочку придётся возить явно — сейчас для этого
есть только `ALFA_TLS_CA_PATH` (общий на сервер); при необходимости цепочку
можно будет перенести в подключение тем же путём, что и сертификат.

## Живая проверка соединения (2026-07-28)

Прогон адаптера против `sandbox.alfabank.ru` с настоящим сертификатом
песочницы. Что выяснилось — ничего из этого не видно на моках:

1. **Закрытый ключ банк отдаёт зашифрованным** (старый формат PEM,
   `Proc-Type: 4,ENCRYPTED`, DES-EDE3-CBC). Без парольной фразы Node падает с
   `bad decrypt`. Поле «Пароль ключа» в форме подключения — обязательное, а не
   украшение. Пароль архива и пароль ключа у Альфы совпадают.
2. **Сервер банка подписан УЦ Минцифры** (`Russian Trusted Root CA`), которого
   нет ни в наборе корней Node, ни в базовом образе. Без него рукопожатие
   падает с `self-signed certificate in certificate chain`.
   Корень **вшит в код** (`russian-trusted-root-ca.ts`), его отпечаток сверен с
   цепочкой рукопожатия и закреплён тестом. Настраивать на сервере ничего не
   нужно. Промежуточный сертификат банк присылает сам.
3. **`ca` в Node заменяет системные корни, а не дополняет их.** Транспорт
   склеивает: системные + Минцифры + `ALFA_TLS_CA_PATH` (если задан) +
   сертификат подключения.

Итог прогона: `Verify return code: 0 (ok)`, банк принял клиентский сертификат и
ответил **401 на фиктивный API Key** — то есть весь путь до приложения банка
рабочий. Осталось подставить настоящий ключ.

Отпечаток сертификата песочницы: `AA:FA:9D:AC:CF:74:67:A1:0B:1C:…`,
действителен до **31.08.2026** — UI предупредит за 30 дней.

## Изоляция пространств (проверено)

Два ИП = два пространства, и пересекаться они не должны ни в одной точке.
Проверено сквозными тестами против реальной БД
(`integrations/cross-tenant.integration.test.ts`, 11 сценариев):

| Что проверено | Результат |
|---|---|
| `list` подключений | видно только свои |
| `update` / `softDelete` / `syncNow` чужого подключения | 404, чужая запись не изменилась |
| Создание подключения на чужой счёт | отказ, запись не создаётся |
| Синк двух пространств подряд | строки легли каждая на своё подключение и счёт |
| Токен и сертификат в запросе к банку | у каждого подключения свои |
| Правило автокатегоризации соседа | к чужим строкам не применяется |
| Плановый крон (все подключения разом) | пространства не смешиваются |
| Inbox: `list` / `count` | только свои строки |
| Inbox: `categorize` / `dismiss` / `undo` чужой строки | 404, строка не тронута |
| Проведение своей строки по чужой категории | отказ |
| Привязка своей строки к чужому заказу | отказ, строка возвращается в Inbox |

Дополнительно: таблицы `IntegrationConnection` и `BankStatementLine` не читаются
нигде за пределами модуля интеграций, а кэш TLS-агентов ключуется хешем пары
cert+key — у разных сертификатов гарантированно разные соединения.

**Побочное поведение, о котором стоит знать.** Идемпотентность строк держится на
паре `(connectionId, externalId)`. Если удалить подключение и завести заново, у
нового будет другой `connectionId`, поэтому операции, уже загруженные в тот же
день, придут во «Входящие» повторно. Практически это заметно только при
пересоздании подключения день в день; лечится либо разбором дублей руками, либо
переносом уникальности на `(workspaceId, accountId, externalId)` — отдельная
задача с миграцией.

## Остаток по счёту (2026-09-06)

`AlfaAdapter.fetchBalance` — `GET {base}/v1/statement/summary?accountNumber=&statementDate=`
(«информация об оборотах», тот же продукт «Выписки по счетам ЮЛ», scope
`transactions`, тот же `ApiKey`). За день банк отдаёт `openingBalance[Rub]` и
`closingBalance[Rub]`, поэтому:

| Что | День | Поле |
|---|---|---|
| Начальный остаток счёта (точный, без вывода по формуле) | день начала выписки (`backfillFrom` / дата подключения) | `openingBalanceRub.amount` |
| «По банку» | сегодня; если сводки за сегодня нет — вчера | `closingBalanceRub.amount` |

Запросы независимы: отказ по одному дню не лишает второго числа, синк строк не
страдает (в лог — WARN `Alfa (остаток …)`). Первая версия ходила в
`/v1/accounts/{номер}` — это метод «Информация по счетам **ФЛ**» (B2C, Bearer),
для ЮЛ его нет, банк отвечал 404.

## Что осталось открытым

- **Живой ответ с данными не получен**: соединение и авторизация сертификатом
  проверены (см. выше), но выписку банк отдаст только с настоящим API Key —
  его выпускают на Портале разработчика. То есть маппинг полей ответа пока
  проверен на образцах из документации, а не на живом теле.
- Признак АУСН банк не отдаёт — сверка Ф4 остаётся на fallback.
- Ф3 (Т-Банк) структурно повторяет этот адаптер на другом маппинге.

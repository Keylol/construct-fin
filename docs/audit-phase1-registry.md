### [A6-export] **High** · security · голоса 3/3
**CSV formula injection: escapeCsv не нейтрализует ведущие = + - @ TAB CR**  
`apps/api/src/reports/export/csv.ts:5`

- **Доказательство:** escapeCsv: `if (/[",\n;]/.test(value)) { return `"${value.replace(/"/g, '""')}"`; } return value;`. Регэксп проверяет ТОЛЬКО кавычку/запятую/перевод строки/точку-с-запятой. Значения вроде имени категории/контрагента приходят в таблицу как есть (builders.ts:82 `name: r.name`, breakdownToTable) и пишутся в CSV без префикса-нейтрализатора. Ячейка, начинающаяся с '=', '+', '-', '@', TAB(0x09) или CR(0x0D) — например имя категории `=HYPERLINK("http://evil","x")` или `@SUM(1+1)*cmd|'/C calc'!A0` — попадёт в CSV дословно (если не содержит запятой/кавычки, даже без обрамления). При открытии в Excel/LibreOffice Calc интерпретируется как формула.
- **Последствие:** Имена категорий и контрагентов полностью контролируются пользователем рабочего пространства. Экспортированный CSV открывают на машинах бухгалтеров/владельцев; формула может вызвать DDE/HYPERLINK-эксфильтрацию данных или выполнение команды. Классическая CSV formula injection в фин-выгрузке.
- **Фикс:** Перед записью текстовых ячеек: если первый символ ∈ {=,+,-,@,\t,\r}, экранировать ведущей одинарной кавычкой ('value) или префиксом TAB; затем применять обычное CSV-quoting. Делать это в escapeCsv (или отдельной neutralizeFormula) для всех текстовых значений, включая title/subtitle/labels.
- **Верификатор:** Дефект подтверждён. csv.ts:7 escapeCsv квотит значение только при совпадении /[",\n;]/ и НЕ добавляет нейтрализующий префикс для ведущих =,+,-,@,TAB,CR: `if (/[",\n;]/.test(value)) { return `"${value.replace(/"/g, '""')}"`; } return value;`. Пользовательские имена доходят до текстовой ячейки без санитизации: builders.ts:82 `name: r.name` → formatCell(...,'text') возвращает `String(value)` без изменений (report-table.ts:44) → escapeCsv. Валидация имени не фильтрует символы: category.dto.ts:20 `name: z.string().trim().min(1).max(100)` (контрагент — .max(200)), поэтому имя `=HYPERLINK("http://evil","x")` (без запятой/кавычки) принимается, сохраняется и пишется в ячейку CSV дословно без префикса. Заголовки/субтитры (csv.ts:15-18) и тот же table.rows в xlsx.ts тоже не санитизируются. Тестов на formula-injection нет — reports.e2e.integration.test.ts:556+ проверяет лишь наличие текста/сумм. Классическая CSV formula injection в фин-выгрузке, открываемой бухгалтерами в Excel/LibreOffice. Severity High корректна: эксплуатация требует открытия файла в spreadsheet и подтверждения DDE/HYPERLINK — не RCE по умолчанию, потому не Critical.

### [A1-money-core] **Medium** · money-correctness · голоса 1/1
**applySupplierReturn пересчитывает avgCost остатка по сумме рефанда, а не по себестоимости — искажает будущий COGS/маржу**  
`apps/api/src/common/wavg.ts:85`

- **Доказательство:** const newValue = sub(mul(oldQty, oldAvg), refundAmount); const safeValue = gt(newValue, D(0)) ? newValue : D(0); return { qty: roundQty(newQty), avgCost: roundCost(div(safeValue, newQty)) }; — из общей стоимости остатка вычитается КАССОВЫЙ refund, а не стоимость выбывающих единиц (returnQty*oldAvg). Когда refund != returnQty*oldAvg, avgCost остатка смещается. Пример: 10 ед.@100 (value 1000), возврат 2 ед. с refund 250 → newValue=750, newQty=8, newAvg=93.75. Остальные 8 единиц теперь оценены 93.75 вместо реальных 100.
- **Последствие:** avgCost остатка питает unitCostAtSale при будущих продажах (applySale), то есть COGS и маржу в P&L. Премиальный/дисконтный рефанд поставщика молча переписывает себестоимость нетронутого товара, искажая будущую прибыль и маржу. При refund > стоимости остатка clamp обнуляет себестоимость всего остатка (avgCost=0 → будущий COGS=0, маржа=100%).
- **Фикс:** Снимать из стоимости остатка cost-basis выбытия (returnQty*oldAvg), оставляя avgCost неизменным: newValue = oldQty*oldAvg - returnQty*oldAvg, avgCost = oldAvg. Разницу между refund и cost-basis (прибыль/убыток по возврату) отражать отдельной денежной проводкой, не трогая себестоимость остатка.
- **Верификатор:** Дефект ПОДТВЕРЖДЁН кодом. wavg.ts:85-87: `const newValue = sub(mul(oldQty, oldAvg), refundAmount); ... avgCost: roundCost(div(safeValue, newQty))`. Из общей стоимости остатка вычитается КАССОВЫЙ refund, а не себестоимость выбывающих единиц (returnQty*oldAvg). Корректная WAVG-механика вернула бы oldAvg неизменным (mul(newQty,oldAvg)/newQty = oldAvg); разница refund − carrying cost должна признаваться отдельной прибылью/убытком, а не размазываться по нетронутым единицам. Тест wavg.test.ts:62 САМ закрепляет искажение: возврат 3 шт по refund 600 из 20@150 даёт avgCost 141.18 вместо 150 на остатке 17 шт. Распространение в P&L реально: warehouse.service.ts:248 `applySale(item.qty, item.avgCost, ...)` снапшотит avgCost в unitCost → OrderItem.unitCostAtSale (order.service.ts:240-254) → COGS/маржа. supplierReturn (warehouse.service.ts:365-366) прямо пишет next.avgCost в item, никакой guard это не предотвращает. Clamp B6 (refund > стоимости остатка → avgCost=0) — это ещё более грубое искажение (будущий COGS=0, маржа=100%), а не защита. Оправдание cash-basis в комментарии (строки 330-337) закрывает только cashflow/чистую прибыль (реальный приток денег по INCOME/SUPPLIER_REFUND корректен), но НЕ маржинальные отчёты, которые строятся именно по unitCostAtSale — то есть по испорченному полю. Дефект условный (нужен refund ≠ returnQty*oldAvg И последующая продажа остатка), но реальный.

### [A2-pnl-period] **Medium** _(исходно High)_ · money-correctness · голоса 3/3
**YoY-сравнение смещено на сутки из-за фикс-миллисекундного сдвига года (некорректно вокруг високосного года)**  
`apps/api/src/reports/period.ts:193`

- **Доказательство:** resolveComparison при mode='yoy' (строки 172-180) сдвигает границы фикс-длительностью: `from: new Date(primary.from.getTime() - yearShiftMs(f.y))`, где `yearShiftMs(y)` (строки 193-196) возвращает длину КАЛЕНДАРНОГО года y-1 (365/366 дней) в миллисекундах. Это не равно «та же календарная дата год назад», когда между датой и её прошлогодним аналогом лежит 29 февраля. Проверено исполнением: для primary 2025-03-15 (f.y=2025 → длина 2024=366 дней) yoy.from получается 2024-03-14 вместо 2024-03-15 (лишний день вычтен, т.к. в интервале нет 29 фев, а взяли 366). Для primary 2024-06-15 (f.y=2024 → длина 2023=365) yoy.from получается 2023-06-16 вместо 2023-06-15 (не хватило дня: в интервале есть 29 фев 2024, а взяли 365).
- **Последствие:** Период сравнения «год назад» уезжает на ±1 сутки в годах, прилегающих к високосному. В колонку сравнения P&L попадает (или из неё выпадает) ровно один день транзакций — выручка/расходы за этот день искажают суммы и проценты MoM/YoY, на которые смотрит владелец бизнеса. Это тихое искажение денег в отчёте, без ошибки.
- **Фикс:** Сдвигать ГОД календарно через tzParts/tzInstant, а не миллисекундами: взять tzParts(primary.from)→{y,mo,d,…}, построить tzInstant(y-1, mo, d, …) (и аналогично для to), сохранив время суток границы. Date.UTC сам нормализует 29 фев → 28 фев в невисокосный год. Удалить yearShiftMs целиком как принципиально неточный.
- **Верификатор:** Дефект ПОДТВЕРЖДЁН прямым исполнением. yearShiftMs(y) (period.ts:193-195) возвращает длину КАЛЕНДАРНОГО года y-1, но в yoy-сдвиге (строки 177-178: primary.from.getTime() - yearShiftMs(f.y)) нужна длина окна между прошлогодней датой и primary, которое содержит/не содержит 29 фев иначе. Прогнал ровно авторские кейсы: primary.from=2025-03-15 (f.y=2025, 2024 високосный → вычитает 366д, но окно 2024-03-15..2025-03-15 без 29 фев = 365д) → yoy.from=2024-03-14 (лишний день); primary.from=2024-06-15 (f.y=2024, 2023 невисокосный → вычитает 365д, но окно 2023-06-15..2024-06-15 содержит 29 фев = 366д) → yoy.from=2023-06-16 (не хватило дня). Оба совпали с заявленным. Контроль: 2026-05-01 (не у високосного) даёт корректный 2025-05-01. Защиты нет: единственный yoy-тест (period.test.ts:97-100) проверяет только май 2026→2025 (не прилегает к високосному), баг не ловит. Соседний код (prev-year:104, enumerateMonths) делает календарный сдвиг корректно — здесь регресс именно в фикс-мс. Эффект: ровно ±1 день транзакций уезжает в колонку сравнения YoY P&L в годы, прилегающие к високосному; тихое искажение без ошибки.

### [A5-reconciliation] **Medium** _(исходно High)_ · money-correctness · голоса 3/3
**asOf трактуется как сырой UTC-инстант без end-of-day в поясе бизнеса (UTC+5) — нарушение R5, занижение computedBalance/discrepancy**  
`apps/api/src/reconciliation/reconciliation.service.ts:64`

- **Доказательство:** `const asOf = asOfInput ? new Date(asOfInput) : new Date();` (стр. 64), далее фильтр `date: { lte: asOf }` (стр. 141 в computedBalanceAt, стр. 164 в opsBetween). DTO `isoDate = z.string().refine((s) => !Number.isNaN(Date.parse(s)))` (reconciliation.dto.ts:7-9) ЯВНО принимает date-only строку вроде "2026-06-15", которую `new Date("2026-06-15")` парсит как `2026-06-15T00:00:00.000Z`. В поясе бизнеса UTC+5 это 05:00 локального времени 15 июня. Весь остальной отчётный слой (reports/period.ts:69-72 endOfDay → tzInstant(...,23,59,59,999) с OFFSET_MS; cashflow.service.ts:10 `interval '5 hours'`) строит границу дня как конец суток в UTC+5. Сверка же берёт сырой инстант. Докстринг сервиса (стр. 10-13) сам утверждает, что считает «как в per-account cashflow», но границу применяет иначе.
- **Последствие:** Пользователь сверяет книгу с банковской выпиской «на 15 июня» и вводит asOf=2026-06-15 (или дату без времени, что DTO разрешает). Все транзакции 15 июня позже 00:00 UTC (т.е. практически весь рабочий день с 05:00 локального) выпадают из computedBalance. Расчётный остаток занижается, discrepancy = факт − книга получает ложное расхождение в размере дневного оборота. Это прямое искажение основного денежного вывода юнита, рассинхрон с cashflow по тому же счёту на ту же дату.
- **Фикс:** Привести asOf к концу суток в поясе бизнеса (UTC+5), как делает reports/period.ts endOfDay, прежде чем применять `lte`. Либо для date-only входа разворачивать в endOfDay(UTC+5), либо документировать и валидировать, что asOf обязан быть полным инстантом-границей. Тот же фикс применить к lastCheck.date в computedBalanceAt.
- **Верификатор:** Дефект подтверждён кодом, но severity завышена. ФАКТЫ: (1) DTO принимает date-only строку: reconciliation.dto.ts:7-9 `isoDate = z.string().refine((s) => !Number.isNaN(Date.parse(s)))` — `Date.parse("2026-06-15")` валиден, asOf (стр.26) опционален и без формата. (2) reconciliation.service.ts:64 `const asOf = asOfInput ? new Date(asOfInput) : new Date();` — `new Date("2026-06-15")` по спецификации ECMAScript = `2026-06-15T00:00:00.000Z`, т.е. 05:00 в поясе бизнеса UTC+5, а НЕ конец суток. (3) Этот сырой инстант идёт в фильтры `date: { lte: asOf }` в computedBalanceAt (стр.140), opsBetween (стр.164) и поиске снимка (стр.70). (4) Контроллер (reconciliation.controller.ts:38) передаёт q.asOf как есть, без нормализации. (5) Остальной отчётный слой строит границу дня как конец суток в UTC+5: period.ts:69-72 endOfDay→tzInstant(...,23,59,59,999) и cashflow.service.ts:10 `interval '5 hours'`. Докстринг сервиса (стр.10-13) сам декларирует паритет с per-account cashflow, но границу применяет иначе → нарушение инварианта R5. ПОЧЕМУ MEDIUM, А НЕ HIGH: занижение проявляется ТОЛЬКО если транзакции 15-го числа хранятся с внутридневным UTC-временем позже 00:00. Но штатный путь ввода — тот же date-only `isoDate`, который transaction.service.ts:115 кладёт через `new Date(input.date)` = тоже `00:00:00.000Z`; тогда `lte 2026-06-15T00:00:00Z` включает транзакцию того же дня корректно. Тесты (reconciliation.e2e.integration.test.ts) везде используют полные midnight-UTC таймстемпы и потому не ловят дефект, но и не доказывают массовое искажение. Реальный триггер (полный ISO с временем или TRANSFER-ноги/импорт с интрадей-временем + asOf date-only того же дня) существует, поэтому дефект реален, но не High.

### [A7-shared-money] **Medium** _(исходно High)_ · money-correctness · голоса 3/3
**rangeFor вычисляет границы периодов в локальном поясе браузера, а не в фиксированном UTC+5 (нарушение R5) — KPI денег у границы периода неверны**  
`apps/web/src/lib/periods.ts:29`

- **Доказательство:** rangeFor использует локальные методы Date: `const day = now.getDay()` (стр.36), `monday.setDate(now.getDate() - offsetToMonday)` (стр.39), `new Date(now.getFullYear(), now.getMonth(), 1)` (стр.43), `Math.floor(now.getMonth() / 3)` (стр.47), `startOfDay`/`endOfDay` через `r.setHours(0,0,0,0)` (стр.18-26). Все эти методы зависят от часового пояса браузера. Это прямо противоречит инварианту R5 и серверной реализации apps/api/src/reports/period.ts:27-32, где граница ЯВНО фиксирована на UTC+5 (`const TZ_OFFSET_MIN = 5 * 60`) и не зависит от TZ окружения. Тест periods.test.ts:9 сам фиксирует `NOW = new Date(2026,5,16,...)` в ЛОКАЛЬНОМ времени и проверяет через `toLocalDateInput`, подтверждая, что границы локальные.
- **Последствие:** Пользователь в Москве (UTC+3) или за границей получит границы 'сегодня'/'месяц'/'неделя', сдвинутые на несколько часов относительно бизнес-пояса UTC+5. Транзакция, проведённая около полуночи, попадёт в KPI 'Доход/Расход/Чистый' (transactions/page.tsx:189-191, dashboard/page.tsx:71-79, summary по range) не того периода, либо выпадет из периода вовсе. Деньги на экране за период будут расходиться с тем, что бэкенд считает принадлежащим периоду (бэкенд пере-привязывает from/to к UTC+5 границам в resolvePeriod, period.ts:123-124). else if (gt(paid, total)) state = 'OVERPAID';


### [D3-lib] **Medium** _(исходно High)_ · concurrency · голоса 3/3
**Idempotency-Key генерируется по вызову mutationFn, а не по логической операции — обещание «retry не задвоит» ложно**  
`apps/web/src/lib/api.ts:84`

- **Доказательство:** newIdempotencyKey() в api.ts задокументирован как «Используй в useMutation, чтобы retry не задвоил операцию (платёж, закупка, finalize)». Но реальное применение — `idempotencyKey: newIdempotencyKey()` ВНУТРИ mutationFn (apps/web/src/hooks/useOrders.ts:107, :118; apps/web/src/hooks/usePurchases.ts:38). React Query вызывает mutationFn заново при каждом retry/повторном mutate(), поэтому каждый повторный сетевой запрос получает НОВЫЙ UUID. Сервер видит другой Idempotency-Key → считает это новой операцией. Ключ обязан быть СТАБИЛЕН на протяжении одной логической операции, иначе он бесполезен против дублей.
- **Последствие:** Платёж по заказу (addPayment), создание закупки (createPurchase) и finalize — денежные операции. При повторной отправке (двойной тап пользователя, ручной mutate() ещё раз, любой механизм повтора на уровне UI) генерируется новый ключ, и сервер проводит вторую транзакцию: двойное списание/задвоенный платёж/задвоенная закупка с движением склада и денег. Глобальная идемпотентность бэка обходится именно из-за нестабильного ключа.
- **Фикс:** Генерировать ключ ОДИН раз на логическую операцию и переиспользовать при повторах: например, фиксировать ключ в замыкании при старте операции (useRef/переменная вне mutationFn, ключуемая по id операции) или принимать его в variables и не пересоздавать в mutationFn. Ключ должен меняться только при намеренно новой операции, а не при каждом вызове mutationFn.
- **Верификатор:** Дефект подтверждён. В apps/web/src/hooks/useOrders.ts:107 и :118 и apps/web/src/hooks/usePurchases.ts:38 вызов `newIdempotencyKey()` стоит ВНУТРИ тела mutationFn (например `mutationFn: ({id,...input}) => api.post(..., input, { idempotencyKey: newIdempotencyKey() })`). Выражение `newIdempotencyKey()` (api.ts:84, crypto.randomUUID) вычисляется заново при КАЖДОМ вызове mutationFn. Поскольку сервер по дизайну различает операции по значению заголовка Idempotency-Key, повторная отправка одной логической операции получает новый UUID → новый ключ → бэк проводит вторую транзакцию (платёж/finalize/закупка с движением денег и склада). Документированный контракт в api.ts:79-80 («Используй в useMutation, чтобы retry не задвоил операцию (платёж, закупка, finalize)») как реализован — ложен: ключ обязан быть стабильным на протяжении одной логической операции, а здесь он нестабилен. Корректная реализация: генерировать ключ один раз на логическую операцию (в onMutate/состоянии компонента/аргументе мутации), а не в теле mutationFn.

Severity скорректирована High→Medium по двум причинам, видимым в коде: (1) автоматический retry мутаций ВЫКЛЮЧЕН — apps/web/src/lib/query-client.ts:17 `mutations: { retry: 0 }`, поэтому сценарий «React Query сам пересылает запрос» не срабатывает; реальный триггер — только ручной повтор/двойной тап. (2) Обработчик onPay (orders/page.tsx:643-662) использует await mutateAsync, что частично сериализует один поток, но кнопка не блокируется по pending, так что двойной быстрый клик до резолва первого запроса действительно даёт два платежа с двумя разными ключами. Защита, заложенная как раз против этого (идемпотентный ключ), нейтрализована. Денежный характер операций сохраняет это как реальный риск задвоения, но требующий действия пользователя, а не гарантированно-системный → Medium.

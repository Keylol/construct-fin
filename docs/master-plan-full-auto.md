# Генплан «Полный автомат» — банки, налог АУСН, регулярка, WB

Последний большой шаг construct-fin (блиц 2026-07-14, 20 решений владельца).
Цель: **минимум работы руками** — операции заходят из банков сами, оператор
только соединяет (приход→заказ, расход→закупка), ядро считает деньги, выручку
и налог. «Гемор остаётся только с наличкой».

## Решения блица (полный список)

1. Оба банка — **расчётные счета ИП** → официальные API (Альфа-Бизнес, Т-Бизнес).
2. Режим: **авто-проводки + Inbox остатка** — что распознали правила, сразу
   проводка; остальное во «Входящие» на разбор в пару кликов.
3. Приход от клиента: **кнопки в Inbox** — «создать заказ из прихода»
   (предзаполненная форма) или «привязать к существующему» (саггест по
   сумме/клиенту/дебиторке).
4. Налоговый режим: **АУСН «Доходы минус расходы»** (20%, минималка 3% с
   доходов, налоговый период — месяц, уплата до 25-го следующего).
5. WB: **распознавание PDF без ИИ** — карты ВБ-банка на физлиц, API нет.
6. Закупка↔заказ: **оба механизма** — привязка банк-расхода к закупке в Inbox
   + план-пометка закупки «под заказ N» (до отгрузки; FIFO-трасса после
   отгрузки уже есть).
7. Наличка: **как сейчас** (обычная форма; документы — вложениями).
8. Сверка налога: **с маркировкой банка** (АУСН-признак операций из API,
   расхождения списком) — ловим ошибки маркировки ДО начисления ФНС.
9. Счета/акты клиентам: **позже** (вне этой программы).
10. Регулярка: **авто-матч из банка** — алерт за 3 дня и в день срока,
    гасится сама при подходящем банковском расходе.
11. Секреты: **мастер-ключ в env, токены в БД шифрованные (AES-256-GCM), UI
    «Настройки → Интеграции»** — ротация без патча и без редеплоя.
    Доступ к UI — **только владелец workspace** (первый ролевой гейт).
12. Синк: **раз в час + кнопка «обновить сейчас»**.
13. Зарплата: **отдельный блок** — справочник сотрудников (ФИО, ставка,
    периодичность аванс/зп) + график выплат + TG-алерты + авто-матч
    SALARY-расходов + история по человеку.
14. WB-сценария **два**: чек покупки → черновик Закупки с позициями;
    выписка ВБ-карты → операции счёта.
15. История банков: **с даты подключения** (прошлое уже в учёте руками;
    чистая граница, банк — единственный источник по счёту с момента включения).
16. Переезд на новый VPS: **позже, отдельным шагом** (не блокирует).
17. Порядок фаз: **Ф1 Фундамент → Ф2 Альфа → Ф3 Т-Банк → Ф4 Налог →
    Ф5 Регулярка+зарплата → Ф6 WB-PDF**.
18. Права: **сотрудник видит и разбирает весь Inbox**; закрыты только
    настройки интеграций/ключи.
19. Налог считаем **с месяца подключения банков** (ставки/сроки — п.4).
20. TG-дайджест Inbox: **пока опустим** (только бейдж в приложении).

## Архитектура

### Модель данных (новое)

| Модель | Суть |
|---|---|
| `IntegrationConnection` | workspaceId, provider (`ALFA` \| `TBANK` \| `WB_CARD`), привязка к `Account`, `credentialEnc` (AES-256-GCM, nonce+tag), маска ключа (last4), status, lastSyncAt, syncCursor, createdById |
| `BankStatementLine` (staging/Inbox) | connectionId, `externalId` (id операции у банка; `@@unique([connectionId, externalId])` — идемпотентность), дата, сумма, знак, контрагент (ИНН/название), назначение платежа, `ausnMark` (доход/расход/не учитывается/null), status `NEW` \| `AUTO_POSTED` \| `RESOLVED` \| `DISMISSED`, `transactionId?` (созданная проводка), raw JSON |
| `RecurringPayment` | название, категория/контрагент, день месяца, сумма + допуск ±%, счёт, `employeeId?`, active |
| `PlannedPayment` | инстанс регулярки на месяц: dueDate, сумма, status `PENDING` \| `PAID` \| `OVERDUE`, `matchedTransactionId?` |
| `Employee` | ФИО, ставка, схема выплат (дни аванса/зп), active; выплаты — RecurringPayment с employeeId |
| `TaxPeriodSnapshot` | месяц, наши Д/Р/налог/минималка, банковские Д/Р по маркировке, расхождения (JSON), status |

Существующее переиспользуем: **Rule-движок** (авто-категории строк), **дедуп
`importHash`** (вторая линия за externalId), **transfer-detect** (ноги между
своими счетами → Переводы), **привязка строки к заказу** (F3), **FIFO/лоты**,
**TelegramAlertService** (расширяется на нотификации регулярки/налога),
**Attachment** (документы к закупкам/операциям).

### Крипто и доступ

- `INTEGRATION_MASTER_KEY` (32 байта, base64) — в `.env.production`. Токены
  шифруются AES-256-GCM с random nonce; в API наружу — только маска.
- Ротация токена банка: вставил новый в UI → следующая синхронизация им
  работает. Без патча, без редеплоя (требование из переписки).
- Ротация мастер-ключа: сервисная команда перешифровки (редкая, с рестартом).
- `OwnerGuard` на весь модуль `/integrations` — первое отступление от плоской
  модели ролей, ТОЛЬКО для секретов (решение №11/№18).
- Ключи не логируются; Trivy/ревью на каждом PR как обычно.

### Синк-пайплайн (общий для всех провайдеров)

```
cron (раз в час) + POST /integrations/:id/sync (кнопка)
  → adapter.fetchStatement(cursor)        # интерфейс BankProviderAdapter
  → upsert BankStatementLine по (connectionId, externalId)
  → transfer-detect (пары между своими счетами → Перевод, обе строки RESOLVED)
  → Rule-движок: распознанные строки → Transaction (авто-проводка, AUTO_POSTED)
  → остальное — NEW в Inbox
```

Проводка, рождённая из строки, несёт ссылку на неё (аудит «откуда цифра»).
Правка/удаление авто-проводки возвращает строку в Inbox (обратимость).

### Экран «Входящие» (Inbox)

Пункт меню с бейджем `NEW`-строк. Строка показывает: дата, сумма, контрагент,
назначение, счёт, саггест правила. Действия:
- **подтвердить категорию** (или исправить) → проводка;
- **создать заказ из прихода** — форма с суммой/клиентом (по ИНН/имени);
- **привязать к заказу** — саггест: открытые заказы этого клиента с
  подходящей дебиторкой, сортировка по близости суммы;
- **создать закупку / привязать к закупке** (для расходов поставщикам);
- **перевод** (если transfer-detect не сработал);
- **не учитывать** (DISMISSED — личное/ошибочное, в отчёты не идёт).

## Фазы

### Ф1 — Фундамент (без внешних ключей, можно начинать сразу)
Схема (`IntegrationConnection`, `BankStatementLine`) + крипто-модуль +
`OwnerGuard` + UI «Настройки → Интеграции» (CRUD подключений, маска ключа) +
синк-каркас (cron + ручной запуск + адаптер-интерфейс + **FakeBankAdapter**
для тестов/демо) + экран Inbox со всеми действиями + авто-проводки через
Rule-движок + transfer-detect. Критерий: на FakeBank полный цикл
«строки → авто-проводки → разбор Inbox → заказ/закупка/перевод» зелёный.

### Ф2 — Альфа-Бизнес API ✅ код готов, ждёт сертификата песочницы
Разведка проведена 2026-07-26, детали и настройка — в [`alfa-api.md`](./alfa-api.md).
Выбран метод `/v1/statement/transactions` с авторизацией по **API Key** (не
OAuth: фоновому крону нельзя зависеть от интерактивного входа). `AlfaAdapter`
идёт **циклом по календарным дням** (банк отдаёт ровно один день за запрос),
курсор = последний закрытый день, mTLS — через `node:https` с сертификатом из
env. Признака АУСН в ответе нет → сверка Ф4 остаётся на fallback.
Остаток: пароль от `test_cert.zip` (запрошен у менеджера) → e2e на песочнице →
подключение счёта «Альфа …4579». История — с даты подключения (реш. №15).

### Ф3 — Т-Банк ✅ код готов, проверен на живой песочнице
Детали — в [`tbank-api.md`](./tbank-api.md). `GET /v1/statement` с Bearer-токеном
из ЛК: mTLS не нужен, период произвольный, пагинация курсорная. Холды
(`operationStatus=Authorization`) в учёт не идут; курсор = дата последней
операции с **окном перекрытия 7 дней** (операция доходит до финального статуса
3–4 дня). Песочница открыта без доступов — адаптер прогнан по живому API.
Остаток: выпустить боевой токен в ЛК (доступ «Счета и выписки») → подключение
счёта «ТБанк …7867».

### Ф4 — Вкладка «Налог» (АУСН Д−Р)
Помесячный расчёт: Д, Р, база, 20%, минималка 3%Д, к уплате `max(…)`,
срок 25-го, TG-алерт о сроке. Сверка с маркировкой банка (`ausnMark`):
таблица расхождений «мы считаем расходом — банк не учёл» и наоборот,
drill-down в операции. Старт — месяц подключения банков (реш. №19).
Риск-fallback: если API не отдаёт АУСН-признак — импорт реестра выгрузкой.

### Ф5 — Регулярка + зарплата + алерты
`RecurringPayment`/`PlannedPayment` + генератор инстансов + TG-алерты
(за 3 дня, в день, при просрочке) + авто-матч банковских расходов
(контрагент + сумма в допуске + окно дат). Блок «Зарплата»: `Employee`,
графики аванс/зп как регулярка с employeeId, история выплат по сотруднику,
страница с итогами. Виджет «к оплате на этой неделе» на дашборде.

### Ф6 — WB-PDF (чеки + выписки)
Парсер текстового слоя PDF (детерминированный, без ИИ): формат «чек покупки»
→ черновик Закупки с позициями (склад), формат «выписка/операции карты» →
`BankStatementLine` для счетов «ВБ Антропов»/«ВБ Каменск» → тот же Inbox.
Вход — через существующий импорт (новый тип источника «WB PDF»).
**Нужны образцы файлов** обоих типов с обеих карт до начала фазы.

## Риски и неизвестные

- **Форматы банковских API** уточнятся только при получении ключей: канал
  авторизации Альфы, лимиты, наличие ausnMark в выписке (ключевой вопрос Ф4),
  сроки жизни токенов (refresh у Альфы?). Ф2 начинается с разведки — план
  адаптера может скорректироваться.
- **WB PDF** — форматы меняются без предупреждения; парсер строим на якорях +
  контрактных тестах на реальных образцах; при изменении формата — быстрый фикс.
- **Дубли на стыке** «ручной ввод ↔ автопоток» в месяц перехода: граница
  «с даты подключения» минимизирует, остаток разруливается в Inbox.
- **Секреты**: компрометация VPS = компрометация ключей (read-only скоупы
  обязательны; мастер-ключ отдельно от БД).
- ФНС/АУСН нормативка меняется — ставки/сроки держим конфигом, не хардкодом.
